## Additional comparison-contract omission: quality also selects native arithmetic policy

The reports correctly describe archive fallback, but an assertion that native quality only changes the model archive would be incomplete.

- LOCAL2.5/core/unet_filter.cpp:262 computes fastMath = quality != Quality::High and :280 supplies it to Graph. The same code is already present in PINNED2.4/core/unet_filter.cpp:262,280, so this is not a new2.5 behavior.
- LOCAL2.5/core/graph.cpp:114,203 passes fastMath into convolution descriptors.
- LOCAL2.5/devices/cuda/cuda_conv.cu:28 derives the requested accumulator type from fastMath; :34-48 uses it when selecting a compatible kernel. This establishes a concrete CUDA policy difference, not a claim that every backend necessarily emits different results.
- Current Rust RT uses quality to select candidates and a preset (R/filters/rt.rs:504-564; R/registry.rs:98-103). Base convolution construction has no quality argument (M/unet.rs:23-27), and lightmap explicitly discards it (R/filters/rtlightmap.rs:242).

Implication: identical native archive bytes do not alone guarantee High/Balanced numerical equivalence. Record native device, quality and arithmetic/precision configuration in comparisons. For a precision-oriented baseline prefer explicitly selected native High, while still holding model bytes fixed. Do not blindly port a fastMath boolean into Burn, claim CUDA policy diagnoses WGPU, or promise bit-exact outputs between backends. This is a documented parity/design gap and experimental confounder; its visual magnitude is unmeasured.

## Highlight and temporal analysis after the user's clarification

**The shared runner has no explicit temporal denoising history.** R/filters/unet_runner.rs:89-100 constructs a fresh TransferState and chooses the scale on every call; :137-138 creates a fresh zero output accumulator. The Base forward pass is convolution/pooling/upsampling/concatenation with fixed loaded parameters (M/unet.rs:104-142), without a recurrent state or a running-statistics layer. This rules out an explicit previous-frame blend in these functions. It does not prove deterministic backend execution, safe external aliasing, or the absence of asynchronous lifetime issues.

**The two tensor interfaces have different handle behavior.** The immutable CommittedRtFilter validates and dispatches the supplied tensors directly (R/filters/rt.rs:650-694). Mutable RtFilter clones stored inputs at :817-819 and clears them at :839-841; subsequent setters mark it uncommitted when the slot is empty (:327-355), causing rebuilding at :799-800. This is an unwanted cache-reuse behavior, not evidence of accumulating image error. The lifetime explanation in comments :829-838 is not proof that execute has completed GPU work or that a caller can safely recycle a foreign buffer. Establish ownership, queue submission and completion contracts from the actual bridge/backend before drawing a read-after-free conclusion.

**If HDR is enabled, highlight sensitivity deserves direct measurement.** R/filters/rt.rs:487-493 selects PU for HDR; R/gpu_ops.rs:51-55 multiplies primary input by scale before the HDR clamp, and :111/:122 apply PU normalization/inverse normalization. R/color.rs:14-16,38-55 sets normalization from65504; this is a normalization anchor, not a hard input clamp at65504. Native does the same construction (LOCAL2.5/core/color.cpp:10-15; core/color.h:180-184,202-206). Values above that anchor are not independently a Rust defect.

The high branch of inverse PU is exponential in Rust (R/gpu_ops.rs:179-196) and native (LOCAL2.5/core/color.h:99-106). Therefore a comparable small error in network-output space can become a much larger *absolute* radiance error in highlights. Differentiating the cited high-branch formula gives dY/dX = (rcpNormScale / PU_E) * (Y + PU_F), before reciprocal input-scale multiplication. This is a mathematical sensitivity observation, not evidence of a bad constant or a discovered kernel error. Direct comparison found the same PU constants (R/color.rs:126-136; LOCAL2.5/core/color.h:77-87) and the same logical branch formulas. It explains why first-divergence measurements should include network-output space and final radiance, rather than judging only final absolute MSE.

Check nonfinite values at multiple stages, not only in the raw input. Finite source values times a large scale, reductions or CNN operations may overflow; inverse exponentiation can also overflow after the existing network-output sanitation (R/gpu_ops.rs:79-96,179-196). Native also applies its sanitation before inverse transfer (LOCAL2.5/devices/gpu/gpu_output_process.h:48-69), so overflow possibility alone is not a newly identified Rust/native discrepancy. R/gpu_ops.rs:29-32 does differ in how existing infinities are replaced. A later diagnostic should count NaN/+Inf/-Inf before scale, after preprocessing, at network output, after inverse transfer and in the presented image.

**Exposure can change between progressive passes without stored history.** The scale is recomputed from current color when HDR is active and no explicit override is present (runner :90-100). As raw accumulated samples and rare bright events change, the histogram/bin means can change, including bins crossing EPS (R/autoexposure.rs:178-193). P5/P6 can perturb that scale; so can the caller supplying sums instead of means, pre-exposed values, or a different working-space convention. These caller behaviors are hypotheses, not observations. A scale curve over sample count and a constant-scale replay are more informative than guessing from one final image.

**If the actual mode is LDR, PU and automatic HDR exposure are not the relevant path.** Inspect the actual hdr/srgb flags and any upstream/downstream tone mapping. R/gpu_ops.rs:53-55 and :91-96 clamp non-HDR values; a bright display highlight is not proof that the denoiser receives HDR data.

Potential external causes that remain unverified: denoised output fed back into the raw progressive accumulator; color/albedo/normal captured at inconsistent sample counts; changing normalization or normal conventions; an overly optimistic clean_aux flag for still-noisy auxiliaries; overlapping asynchronous reads/writes of reused buffers; and display recomposition/tone mapping. Their priority follows the time-dependent symptom, not a source-confirmed bug. The renderer bridge is outside this review's inspected files.

Native kernels can have different precision/fusion and device-dependent alignment (LOCAL2.5/core/unet_filter.cpp:267), so choose deliberate tolerances and matching output regions. No bit-exact cross-backend promise follows from source topology.

## Architecture assessment

The proposed use of one common numerical runner and immutable committed artifacts is sound. It should be implemented as a few explicit contracts within existing modules, not as a framework rewrite:

- **Mode/input contract:** primary role, auxiliary roles, transfer kind, signed mode, sanitation policy, expected channels/shape and destination semantics. Derive it once before both ordinary and custom weight routes. The current positional runner interface R/filters/unet_runner.rs:40-54 is already long and omits signed/destination semantics; a compact validated context is safer than adding more adjacent booleans.
- **Resolved model contract:** bytes, selected stem/source/hash, validated topology/channel widths/kernel structure and RF. Keep file resolution separate from numerical inference. Share the existing resolver with explicit source precedence and non-NotFound error handling.
- **Committed execution contract:** validated geometry/model/mode plus the device and tile plan, separate from per-frame tensor handles and exposure overrides. A consumed frame handle must not erase the model signature.

One qualification: archive tensor shapes can establish executable dimensions, but cannot infer whether a same-shaped model was trained for HDR versus LDR, albedo versus normal, or clean versus noisy auxiliaries. Preserve semantic model identity/provenance and the caller's explicit custom-weight contract; structural validation alone cannot prove those semantics. Likewise RF derived from a known topology is safe only after validating the kernel/stride/pooling assumptions that define that topology.

Fix the mode/padding/exposure/RF contracts in small independently reviewable changes with frozen baselines. Defer incidental ownership/statistics/fixture deduplication until causal comparisons are preserved. Sharing mathematical contracts is essential; retaining scalar and tensor implementations as independent representations can be useful for detecting implementation errors. Do not let the “oracle” duplicate the same incorrect pooling shortcut.
